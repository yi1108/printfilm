# 后台统一钱包迁移与核对

入口：系统管理的“支付与通知”页面，下方“统一钱包迁移与核对”。需要管理员权限。

本入口迁移的是历史业务账目，不是数据库建表。启动自动建表不代表历史余额已经核对。
不会重新履约历史充值，不会按积分面值猜测现金，不会将 Sandbox 资金改为 Production。
保持原 AI 定价、团队付款人和消费单位。无法解释的余额或冻结关系会阻止整个批次。

## 操作流程

1. 发布 API 和管理后台新版本。不要在迁移期间滚动更新部署。
2. 点击“刷新只读核对报告”，查看可迁移、异常、已核对数量及在途任务状态。输入用户 ID 可定位账号，例如 650。只读检查不创建账户、来源或流水。已有统一钱包账户的用户显示当前积分；环境、来源可用额度或冻结对不上时，异常原因写出来源类型、额度、实付和环境。
3. 在业务低峰填写操作理由，点击“暂停写入”。暂停状态写入数据库，进程重启不会自动解除。
4. 等待在途任务结算；排队任务不会继续启动，请通过任务页取消，运行中的任务允许完成或取消。存在 pending/leased/running/awaiting_poll/awaiting_review/cancel_requested 或未结算冻结/预留任务，均不能迁移。
5. 刷新报告。仍有冻结额度，或 Apple 观影币来源对不上的账号保持「需人工核对」，必须先处理。其余无法回放的账号标为「按当前余额迁移」：正余额记成一条无实付的 `legacy_opening` 历史结余，负余额记成欠费，可用积分写成 0。迁移后的可用积分不会低于原来的正余额。异常原因会写明最早一笔扣费前的余额、是否缺少赠送或充值流水，以及未入账的已支付订单。可追溯账号仍按充值、赠额和 Apple 来源迁移。不能通过手工补「已核对」标记绕过。
6. 点击“备份并迁移”。服务端先取得排他锁和相关表锁，再复查在途任务；调用 pg_dump 生成完整数据库 custom-format 备份，pg_restore --list 检查可读性并计算 SHA256。备份失败则不写入迁移数据。
7. 在锁内重新回放历史订单、赠额及消费流水，复核旧观影币来源；所有账户通过后，在同一事务建立来源、分摊、明确欠费和账户记录，并开启统一钱包。任一失败整体回滚，暂停状态保留。
8. 成功后仍处于维护状态。下载数据库备份，检查报告与迁移流水，点击“复核并恢复服务”。恢复操作会再次核对；不会只依赖之前的预览结果。
9. 重新加载支付配置页面，避免旧表单覆盖新状态。验证 Web 钱包、AI 扣费、Web 充值及 App 充值/解锁。真实渠道操作需用各自真实凭证。

没有执行成功时，“取消维护”仅恢复维护前的运行模式，不改账户环境或资金记录。原来就错误开启统一钱包的部署不会因取消维护自动修复。

## 维护范围及并发

- 维护期间拒绝全站 API 写请求，包括注册、上传、评论、配置保存、充值、新任务和视频解锁，返回 503 和 Retry-After: 30。浏览、查询和登录保持可用。
- 保留统一任务取消接口，便于排空任务；维护入口本身不受拦截，但仍要求管理员认证。
- GET 易支付通知和 POST Apple/Stripe 通知也返回可重试失败，不返回伪造的支付成功。迁移结束后依赖渠道重试、客户端重新验单及服务端补偿完成有效付款；迁移后需核对渠道待处理订单。
- Apple 后台通知及补偿循环与 HTTP 写请求共用数据库 advisory 读写锁。迁移排他锁等待已接纳请求退出，新写请求不能穿过切换边界。
- API 与任务进程看到已提交的迁移版本后刷新本进程资金配置；调度器在维护期间停止启动新任务，但已有执行和结算继续运行。
- 备份和迁移为同步请求，耗时取决于数据库大小。网关应给此管理接口留足超时（建议至少 10 分钟）。响应丢失时先刷新报告；使用同一迁移编号重试不会再次充值。不得根据浏览器超时判断数据库一定未提交。

## 备份部署

API Dockerfile 安装官方 PostgreSQL 18 客户端，支持备份不高于该版本的服务器；版本不兼容、权限不足、磁盘不足或工具缺失均停止迁移。手动启动的主机也必须可执行 pg_dump 和 pg_restore。

备份目录为 backend/var/wallet-backups（镜像内 /app/var/wallet-backups），不是静态资源目录。Dockerfile 声明此目录为卷；生产 Compose/容器管理页面应将它绑定到明确的持久目录，所有 API 副本共享该目录，并纳入服务器备份策略。不要删除该卷或在迁移中更换容器。

数据库连接信息只通过子进程环境传入，命令参数和日志不包含数据库密码。备份仅由管理员鉴权接口下载，不能配置为公开下载地址。SHA256 存在迁移状态和资金迁移引用中。pg_restore --list 只检查归档可读性，不等同于恢复演练；生产切换前仍应在独立数据库验证备份恢复。

## 接口

- GET /api/admin/settings/wallet-migration：只读报告，包含 state、missing_schema、ready、blocked、already_migrated、active_tasks、accounts。
- POST /api/admin/settings/wallet-migration/pause：请求 {"reason":"计划资金切换"}，返回 job_id 和暂停状态。
- POST /api/admin/settings/wallet-migration/apply：请求 {"job_id":"报告中的迁移编号","reason":"来源与余额核对通过"}。
- POST /api/admin/settings/wallet-migration/resume：请求同上，复核恢复或取消未执行的维护。
- GET /api/admin/settings/wallet-migration/backup：管理员下载当前成功迁移的备份。

修改状态需操作理由，job_id 用于拒绝旧页面操作。失败返回 409，资金事务回滚，操作审计保留失败信息（不得展示底层连接串或密钥）。结构缺失会列在报告中，不自动猜测补账。

普通配置保存和环境导入在从关闭切为启用统一钱包时执行历史账户检查：待迁移、异常或在途任务存在即拒绝。即使报告通过，也必须从迁移入口原子切换，防止检查完成到保存之间仍有旧模式注册或付款进入。已有统一钱包账户时也拒绝切回旧记账。不再让未迁移部署直接开启后影响所有用户生成。
