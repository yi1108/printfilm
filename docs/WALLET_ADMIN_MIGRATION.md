# 后台统一钱包迁移与核对

入口：系统管理的“支付与通知”页面，下方“统一钱包迁移与核对”。需要管理员权限。

本入口迁移的是历史业务账目，不是数据库建表。旧脚本 `prepare_unified_wallet_schema --apply` 已停用，防止绕过维护、逐户确认和备份审计；`--schema`、`--check`、`--report` 保留。启动自动建表不代表历史余额已经核对。
不会重新履约历史充值，不会按积分面值猜测现金，不会将 Sandbox 资金改为 Production。
保持原 AI 定价、团队付款人和消费单位。无法解释的余额或冻结关系会阻止整个批次。

## 操作流程

1. 发布 API 和管理后台新版本。不要在迁移期间滚动更新部署。
2. 点击“刷新只读核对报告”，查看可迁移、异常、已核对数量及在途任务状态。输入用户 ID 可定位账号，例如 650。只读检查不创建账户、来源或流水。已有统一钱包账户的用户显示当前积分；环境、来源可用额度或冻结对不上时，异常原因写出来源类型、额度、实付和环境。
3. 在业务低峰填写操作理由，点击“暂停写入”。暂停状态写入数据库，进程重启不会自动解除。
4. 等待在途任务结算；排队任务不会继续启动，请通过任务页取消，运行中的任务允许完成或取消。存在 pending/leased/running/awaiting_poll/awaiting_review/cancel_requested 或未结算冻结/预留任务，均不能迁移。
5. 刷新报告。Sandbox 充值进入正式流水、重复入账、订单凭证冲突、流水中间断裂、区间损坏、未入账正式订单或冻结关系不明，均保持「需人工核对」，不能人工点确认绕过。只有缺失期初历史、后续流水连续且能完整回放的账户显示「历史期初待确认」。填写核对依据后逐户确认：已知充值保留真实实付和消费分摊，仅未知期初部分建立 `legacy_opening`，标记 `pending_fx`（待核算），绝不认定为零成本赠额。负余额转明确欠费，可用积分为 0，不免除债务。确认绑定本次任务、用户、环境、余额、订单与来源报告指纹，任一事实改变后原确认失效。未确认账户不进入执行计划。
6. 点击“备份并迁移”。服务端先取得排他锁和相关表锁，再复查在途任务；调用 pg_dump 生成完整数据库 custom-format 备份，pg_restore --list 检查可读性并计算 SHA256。备份失败则不写入迁移数据。
7. 在锁内重新回放历史订单、赠额及消费流水，复核旧观影币来源；所有账户通过后，在同一事务建立来源、分摊、明确欠费和账户记录，并开启统一钱包。任一失败整体回滚，暂停状态保留。
8. 成功后仍处于维护状态。下载数据库备份，检查报告与迁移流水，点击“复核并恢复服务”。恢复操作会再次核对；不会只依赖之前的预览结果。
9. 重新加载支付配置页面，避免旧表单覆盖新状态。验证 Web 钱包、AI 扣费、Web 充值及 App 充值/解锁。真实渠道操作需用各自真实凭证。

没有执行成功时，“取消维护”仅恢复维护前的运行模式，不改账户环境或资金记录。原来就错误开启统一钱包的部署不会因取消维护自动修复。

## 维护范围及并发

- 维护期间拒绝全站 API 写请求，包括注册、上传、评论、配置保存、充值、新任务和视频解锁，返回 503 和 Retry-After: 30。浏览、查询和登录保持可用。
- 保留统一任务取消接口，便于排空任务；维护入口本身不受拦截，但仍要求管理员认证。
- GET 易支付通知和 POST Apple/Stripe 通知也返回可重试失败，不返回伪造的支付成功。迁移结束后依赖渠道重试、客户端重新验单及服务端补偿完成有效付款；迁移后需核对渠道待处理订单。
- Apple 后台通知及补偿循环与 HTTP 写请求共用数据库 advisory 读写锁。迁移排他锁等待已接纳请求退出，新写请求不能穿过切换边界。
- API 与任务进程看到已提交的迁移版本后刷新本进程资金配置；调度器在维护期间停止启动新任务，但已有执行和结算继续运行。
- 备份和迁移为同步请求，耗时取决于数据库大小。网关应给此管理接口留足超时（建议至少 10 分钟）。响应丢失时先刷新报告；使用同一迁移编号重试不会再次充值。不得根据浏览器超时判断数据库一定未提交。

## 备份部署

备份执行前检查 pg_dump、pg_restore 是否存在及目录可写。API Dockerfile 安装官方 PostgreSQL 18 客户端，支持备份不高于该版本的服务器；版本不兼容、权限不足、磁盘不足或工具缺失均停止迁移。手动启动的主机也必须可执行 pg_dump 和 pg_restore。

备份目录为 backend/var/wallet-backups（镜像内 /app/var/wallet-backups），不是静态资源目录。Dockerfile 声明此目录为卷；生产 Compose/容器管理页面应将它绑定到明确的持久目录，所有 API 副本共享该目录，并纳入服务器备份策略。不要删除该卷或在迁移中更换容器。

数据库连接信息只通过子进程环境传入，命令参数和日志不包含数据库密码。备份仅由管理员鉴权接口下载，不能配置为公开下载地址。SHA256 存在迁移状态、资金迁移引用及备份目录的独立 JSON 清单中。清单不依赖资金事务提交，因此备份成功、迁移失败后仍可下载。重试同一任务会保留上一份归档及校验值并生成新快照，不拿旧快照代替当前备份。后台显示历史任务、备份状态和执行结果，下载前重新验证 SHA256。清单和 dump 必须一起持久化、一起备份。进程突然中断时可能显示准备中或执行未完成，应先核对数据库状态；不得据此直接重做充值。pg_restore --list 只检查归档可读性，不等同于恢复演练；生产切换前仍应在独立数据库验证备份恢复。

## 接口

- GET /api/admin/settings/wallet-migration：只读报告，包含 state、missing_schema、ready、opening、approval_required、blocked、already_migrated、active_tasks、accounts、fingerprint 和 backups。账户行含原积分、冻结、迁移后可用、原欠费、剩余欠费、待核算来源数、环境和确认状态；未计算字段显示「未计算」，不是 0。
- POST /api/admin/settings/wallet-migration/pause：请求 {"reason":"计划资金切换"}，返回 job_id 和暂停状态。
- POST /api/admin/settings/wallet-migration/approvals/{user_id}：仅在暂停且当前任务未完成时逐户确认。请求 `{"job_id":"当前任务编号","environment":"Production","fingerprint":"账户行的64位SHA256","reason":"经核对，期初历史缺失，保留待核算结余"}`。状态不是 opening 或报告改变时返回 409。
- POST /api/admin/settings/wallet-migration/apply：请求 {"job_id":"报告中的迁移编号","reason":"来源与余额核对通过"}。
- POST /api/admin/settings/wallet-migration/resume：请求同上，复核恢复或取消未执行的维护。
- GET /api/admin/settings/wallet-migration/backup：管理员下载当前任务的备份；添加 `?job_id=<备份列表中的编号>` 下载历史备份，包括资金事务失败前已完成的备份。备份损坏返回 409，未完成返回 404。

修改状态需操作理由，job_id 用于拒绝旧页面操作。失败返回 409，资金事务回滚，操作审计保留失败信息（不得展示底层连接串或密钥）。结构缺失会列在报告中，不自动猜测补账。

普通配置保存和环境导入在从关闭切为启用统一钱包时执行历史账户检查：待迁移、异常或在途任务存在即拒绝。即使报告通过，也必须从迁移入口原子切换，防止检查完成到保存之间仍有旧模式注册或付款进入。已有统一钱包账户时也拒绝切回旧记账。不再让未迁移部署直接开启后影响所有用户生成。

本次只交付代码和验证；没有执行线上迁移、修改余额或开启线上维护。

## 实付、区间与收益核对

- Web 充值只匹配 `topup + ref_type=order` 的流水及 `web_order` 来源，不能拿任务引用编号当订单证据。检查个人归属、支付渠道、Production 环境、付款状态、到账额度及重复记录。
- 人民币使用订单的实付快照（旧记录缺少快照时沿用原人民币金额）；美元使用订单保存的原币金额及汇率，累计取整规则与正常履约共用同一估值函数。缺少汇率时不按套餐人民币价猜测，来源保留 `pending_fx`。
- `pending_fx` 的 0 仅是尚未核算的技术占位，不表示已经确认现金成本为 0。原币、汇率等证据仍在原订单。来源未核清前，既有收益打款校验禁止结算其关联收益；本入口不自动改写已发生的消费成本或已打款记录。
- 每批来源完整校验可用、冻结/消费、作废区间的边界、重叠与缺口，并核对消费成本、欠费及逐笔偿还的归属、金额和状态。退回记录保留，但不能重复占用来源区间。
- 锁内查询强制刷新 ORM 缓存；不会执行锁前预览的旧余额或旧计划。既有观影币镜像保留只读，已迁入且与渠道凭证一致的来源不会重复合并。

## 验证及上线门槛

运行 `test_wallet_migration_safety.py`、`test_wallet_cutover.py`、`test_unified_wallet_migration.py`、`test_wallet_cutover_postgres.py` 和管理后台构建。后两组数据库测试需要可连接的独立 PostgreSQL 测试库；连接失败不能记为通过。测试夹具使用随机 schema，不对正式账户执行迁移。

必须在测试部署完成暂停、并发阻断、逐户确认、成功切换、失败回滚、失败备份下载及重试验证。恢复演练应使用测试生成的 dump 和全新的隔离空库，执行 pg_restore 后检查来源、余额、欠费及偿还合计；`pg_restore --list` 不代替真实恢复验证。上述数据库测试及恢复演练通过前，不开放正式批量迁移。

## 按原积分确认迁移（平台承担沙箱替代赠额）

该操作是管理员明确批准的新余额基线，不会把异常标成正常回放。适用于历史冻结归属丢失、流水断裂，以及旧 Sandbox 账户误用于正式业务的情况；当前实际冻结和任务必须已结算。

1. 发布 API 和管理后台。启动时以既有统一数据库锁幂等新增 `wallet_migration_resolutions`，不自动修改任何余额。
2. 刷新报告，先暂停写入并排空任务。每行可展开“按原积分迁移预览”，查看原积分、迁移后可用、欠费、平台补赠和待核算部分。
3. 选择账户，或选择当前筛选下可执行的账户（每批最多 500 个）。填写核对依据；涉及赠额时勾选“沙箱替代额度由平台补发正式赠额”。点击“确认所选账户按原积分迁移”。确认仅保存决策，不写资金。
4. 分批确认直到无未确认账户及阻断异常，再点击既有“备份并迁移”。服务端在同一排他锁和表锁内重新计算指纹，不使用过期预览。
5. 成功后复核并恢复服务。已迁移账户可下载原始快照及处理记录，再次请求不会重复补赠。

金额规则：原积分 9500 迁移后仍是 9500，不是再加 9500。旧沙箱账户的替代额度记正式 `admin_grant`，实付成本 0，由平台承担；Apple 原沙箱交易、订单及历史流水保持原状。新增基线调整流水与平台赠额流水相互抵消，总变化只反映原负余额转明确欠费等必要转换。原积分 -1124 则可用 0、欠费 1124，不免除原消费。

已能证明的正式充值来源及实付成本保留；其余不能解释的余额记 `legacy_opening/pending_fx`，不是已核算的零成本赠额，相关创作者收益仍不能结算。真实付款来源损坏、真实订单尚未入账、已有欠费偿还关系、退款待办或实际冻结，不允许被原积分确认掩盖；报告写明具体阻断原因。正式独立观影币尚有余额时先按原来源合并，不能在本操作中遗漏付款。

旧 Sandbox 来源保留原环境；正式消费只分摊 Production 来源。旧正式赠额若需归档，仅关闭其可变可用状态，原状态完整保存在不可变迁移快照中。历史账目不删除、不覆盖。账户环境的变更、归档来源编号、原订单及流水、原积分、操作人、理由、指纹和备份引用均有记录。每个账户仅允许建立一次此类基线；后续新产生的异常不能再次套用旧确认。

新增接口（均需管理员权限）：

- `POST /api/admin/settings/wallet-migration/balance-approvals`：`{"job_id":"当前迁移编号","reason":"核对后保留原积分，由平台承担沙箱替代赠额","accept_platform_grant":true,"selections":[{"user_id":1276,"fingerprint":"该行 balance_migration.fingerprint"}]}`。逐项全部校验通过后才原子保存本批确认；任一项变化整批返回 409。
- `GET /api/admin/settings/wallet-migration/balance-resolutions/{user_id}`：原始财务快照、处理结果、操作人、理由与备份引用。只读，不重新履约付款。
- 核对报告增加 `balance_approved` 计数、行级 `balance_migration` 预览及 `balance_resolution` 已执行记录。

测试新增覆盖 SQLite 真实 ORM 往返、Sandbox 来源隔离、负数转欠费、流水保留、调整与赠额不重复加款、批量确认原子性、指纹失效及失败回滚。SQLite 不证明 PostgreSQL advisory 锁和并发行为；生产切换仍需 PostgreSQL 集成测试及真实备份恢复演练。
# 真实付款存在但历史余额链不连续

无现存统一资金来源批次、原订单与唯一充值入账流水一致，但历史余额链不连续时，可在原积分确认入口逐户确认。原订单、币种、实付和流水保存在迁移快照中；剩余积分记为 `legacy_opening / pending_fx`，不是零成本赠额。负余额迁移为可用 0 和明确欠费，不补赠。

预览返回 `pending_order_ids`、`pending_payment_reason`；这些订单不再作为新来源重复回放，但原记录仍保留。成本与消费分摊未还原前，不得据此结算相关创作者收益。负余额账户同样保留待核算订单记录，不能因剩余积分为 0 认定成本已核清。

仅余额链断裂可使用此路径。重复入账、订单归属/渠道/环境/额度冲突、缺少真实入账凭证、Apple 交易缺失、已有真实资金来源损坏仍须修复证据，不允许自动兜底。确认仍绑定报告指纹、操作人和理由，在暂停、排空任务、备份之后才执行。
